# Predictive analytics

The Predictive Analytics page starts in an all-category, all-province overview. Its controls select Revenue, Orders, or Quantity; a product category; a province; a forecasting model; and a 3, 6, 9, or 12 month horizon. The selected category, province, model, and horizon update the ranking, detail panel, chart, validation, and forecast range. The shared Analysis Controls scope still filters geography, categories, dates, and return treatment.

The page reads `GET /api/forecasts`. The backend uses the existing Supabase `master_transactions` cache and sync guard. It does not write predictions or change database tables. The explicit Refresh data action forces a fresh source read; ordinary control changes use the shared 30-second cache. Forecasting models are ARIMA(1,1,1), Prophet-style trend plus yearly seasonality, and Random Forest Regression. The forest uses deterministic bootstrap trees so repeated requests return the same values.

The browser keeps up to 24 analytics responses in memory for five minutes. Returning to an already visited analytics tab reuses its loaded view and response. Refresh data forces a fresh source read and clears other cached analytics responses. A successful Data Preparation sync also clears the browser cache.

Supabase pages are loaded six at a time. Predictive summary calculations skip the full geographic breakdown for each province/category series, and identical forecast requests are reused by the server while the underlying data snapshot is unchanged.

Targets are monthly PHP revenue, distinct orders, or net units. Each forecast is calculated for a province × product category combination, with region retained to disambiguate provinces. The overview ranks available combinations by average monthly forecast demand across the chosen horizon. Category and province comparison tables use aggregated series for their displayed level.

A series needs at least 3 consecutive calendar months with transaction records to produce an exploratory forecast. Fewer than 6 months is labeled very low reliability; fewer than 18 is labeled low reliability. Three months cannot support a meaningful holdout backtest, so accuracy metrics are unavailable and the estimate should be treated as highly uncertain. A month with records and zero demand is valid; a month without records is unknown and blocks the forecast. Negative monthly totals and partial custom calendar-month ranges also block it. Insufficient-history combinations appear in a separate list with order, active-month, and reason details. The chart follows the current selections and starts forecasting in the month after the last observed month.

When enough history exists, the selected model is trained on all but the final holdout. Series with 6–35 observations use up to the final six months for validation while retaining at least three training months; series with 36 or more use the final twelve months. With only 3–5 observations, a holdout is not meaningful, so the model is fit on all observations and no accuracy percentage is reported. ARIMA uses a differenced ARIMA(1,1,1) estimate, Prophet uses a linear trend with yearly Fourier seasonality, and Random Forest uses a recursive regression forest over lagged demand and calendar features.

Reliability reports holdout MAPE, MAE, RMSE, period, and actual-versus-predicted values for the selected model. MAPE excludes zero actuals and reports no value when every holdout actual is zero. The current monthly baseline is the average of up to the latest 12 observed months; forecast demand is the average across the chosen horizon. Forecast growth compares those averages, and end demand is the estimate for the final forecast month. Growth above 2% is labeled increasing, below -2% decreasing, and between those values stable.

The displayed lower and upper range uses holdout RMSE multiplied by the square root of the forecast step when a backtest is available. With only 3–5 months, it uses historical variability with a 25% minimum buffer as an illustrative display heuristic. Neither range is a calibrated confidence interval, and actual demand can fall outside it. Transaction dates do not prove that boundary months are fully uploaded, so users should verify their source data.

Predictive Analytics presents evidence for later prescriptive analysis. It does not recommend advertising budgets, inventory quantities, warehouses, ROI, or business strategy.

Prescriptive Analytics uses the target, horizon, and model most recently applied with Generate Forecast. Both endpoints use the same pair-level forecast calculation, so current demand and forecast growth for a matching province × category pair use the same series and settings. Prescriptive still combines those forecast signals with year-over-year growth, demand consistency, and category affinity; when a pair has no usable forecast, it can use historical growth evidence instead.
